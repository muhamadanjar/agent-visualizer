- Model Endpoint management and Definition configuration are owner-scoped. Definition configuration is saved as a new immutable version; disabling and archiving are separate lifecycle actions. Duplicate Definition names are permitted and each record keeps a UUID.
- Factory/preflight resolves the active Definition Version and owner-scoped Model Endpoint, intersects configured tools with project policy, and freezes non-secret configuration in the Run snapshot. Dispatch claims enforce the configured concurrency limit per Definition Version. This does not prove a LangChain runtime is constructed.

- New PRD is canonical; `PRD.md` was removed. Active references and roadmap are remapped; old work logs remain historical evidence.

- One avatar represents one `Agent Instance`, replacing PRD §34's proposed one-avatar-per-definition default.
- LangChain replaces the current custom loop directly; API cutover is breaking and all known callers move together. Migrations preserve IDs/history; migration 0011 removes Agent Definition name uniqueness to follow the PRD's UUID-identity requirement.

- Credential values remain in allowlisted server environment variables; database/API store references only.
- PostgreSQL is the canonical Activity Event store; Redis Streams is fan-out. Redis failure must not lose committed events.
- Every delegated child Run requires approval. Allowlisted safe tools run without per-call approval; sensitive operations require specific approval or denial.
- `cancelled` is terminal only after worker stop is acknowledged/verified. Unknown outcomes are not blindly retried.
- The agreed local Event System profile is 10 WebSocket clients, 100 newly published events/second, p95 delivery ≤1 second; it is temporary and not a production capacity target. Pilot hardware/network remain unselected. Demo-mode simulation, if enabled, is clearly separated and never proves real execution.

## Historical planning decisions (superseded where conflicting with the PRD v1.0 decisions below)

### Decisions from earlier scope, retained as historical evidence

These decisions were explicitly selected by the user during planning; they are planning constraints, not claims that implementation or feasibility has been verified.

- Agent Office orchestrates real Task execution and uses the live 3D office as the primary view of verified activity; simulated events are not operational evidence.
- Agent Definition is a reusable system-prompt template; Skill catalogs/attachments are optional P1. Adding an agent creates a persistent idle Agent Instance; work starts only through an explicit Task/Run.
- Agent Office Execution Engine/Runner owns the task/tool loop and canonical events; Provider Adapters supply inference only. P0 begins with one configured endpoint.
- Several Agent Instances may run independent Tasks at once; child delegation is deferred to P1.
- Tools allowlisted for the selected workspace/Run do not require approval per call. Destructive/out-of-scope actions and new egress remain restricted or approval-gated.
- P0 3D acceptance shows at least two independent live Runs from verified lifecycle/safe-action events. Stale data is labeled and work animation freezes; hidden reasoning and sensitive tool output are never exposed.
- Use the PRD's recommended stack as a baseline subject to validation: Next.js/TypeScript, React Three Fiber, FastAPI, PostgreSQL, Python dispatcher/runner, and Docker Compose.
- Database persistence direction (2026-10-27): SQLModel is the default model/schema path; retain raw SQL for specialized PostgreSQL operations and preserve the existing checksummed migration history. Implementation decision: future schema migrations use Alembic with SQLModel metadata; historical SQL migrations remain in the compatibility runner.
- Earlier Phase 1 planning excluded coding-agent products as core integrations. OMP/Codex findings remain only in historical entries in this register; their probe sources were removed on 2026-10-27. Provider support remains limited to tested adapter/endpoint/model/features.
- The initial Phase 1 inference target is OpenAI-compatible Chat Completions through a Provider Adapter; native APIs require their own adapter.
- Pilot target: one owner, one private workspace, several projects, and one repository/workspace through the runner.
- Start with a single private Linux host and an isolated runner process; reconsider a separate runner host if evidence requires it.
- Start with a simple, readable 3D template; defer detailed art direction until a visual/performance spike.
- Alur awal menjalankan system-prompt definition tanpa katalog Skill; Skill import/pin/compatibility adalah P1. File skrip tidak dieksekusi hanya karena diimpor.
- Assignment is explicit; delegation is explicit and limited to registered/allowed agent definitions.
- Enforce runtime limits; choose monetary budget values before pilot. Do not promise hard spend limits unsupported by the runtime.
- Use configurable PRD retention proposals as pilot defaults: 30 days for detailed events/logs and 90 days for definitions, run summaries, approvals, and artifacts.
- Do not estimate calendar duration before M0 evidence and team capacity are known.
- No pilot client device has been selected; user selected the available 1440×900 CSS / DPR 1.25 managed-browser profile as the provisional M0 performance target, not as a substitute for final pilot hardware.
- Phase 1/M0 was open as of 2026-10-23; it was subsequently closed on 2026-10-26 for the user-redirected provider/3D feasibility scope only. Managed execution and spend-control gates remain open.
- After the NFR-04-shaped measurement, the user selected the available browser profile provisionally for M0; the actual pilot device remains unselected.

- UI-first direction (2026-10-23): desktop 3D office home; data views one click away; warm low-poly style; deterministic local records labeled “Sample” where canonical APIs do not yet exist; work-changing actions stay disabled without real persistence/authorization. The product model was refined on 2026-10-26; sample UI remains separate from operational runtime behavior.
