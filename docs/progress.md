## Confirmed decisions

These decisions were explicitly selected by the user during planning; they are planning constraints, not claims that implementation or feasibility has been verified.

- MVP requires real Managed runtime behavior; simulated events do not qualify as operational MVP.
- Use the PRD's recommended stack as a baseline subject to validation: Next.js/TypeScript, React Three Fiber, FastAPI, PostgreSQL, Python dispatcher/runner, and Docker Compose.
- Core runtime integration is vendor-neutral through the Runtime Adapter contract. OMP is the existing prototype candidate; Codex app-server is an untested candidate; ACP is usable only with a compatible execution runtime. No product runtime is supported until its lifecycle, capability, and safety gates pass.
- Provider scope is protocol-neutral: a configured provider is usable only through an available Provider Adapter whose capabilities, credentials, and egress policy have been verified. OpenAI-compatible APIs are optional; no claim is made that every provider works without an adapter.
- Pilot target: one owner, one private workspace, several projects, and one repository/workspace through the runner.
- Start with a single private Linux host and an isolated runner process; reconsider a separate runner host if evidence requires it.
- Start with a simple, readable 3D template; defer detailed art direction until a visual/performance spike.
- MVP skill imports are Markdown and text resources; uploaded scripts do not execute merely because they were imported.
- Assignment is explicit; delegation is explicit and limited to registered/allowed agent definitions.
- Enforce runtime limits; choose monetary budget values before pilot. Do not promise hard spend limits unsupported by the runtime.
- Use configurable PRD retention proposals as pilot defaults: 30 days for detailed events/logs and 90 days for definitions, run summaries, approvals, and artifacts.
- Do not estimate calendar duration before M0 evidence and team capacity are known.
- No pilot client device has been selected; user selected the available 1440×900 CSS / DPR 1.25 managed-browser profile as the provisional M0 performance target, not as a substitute for final pilot hardware.
- Earlier user instruction required Phase 1/M0 exit criteria before proceeding to Phase 2. The user explicitly superseded that sequencing instruction on 2026-10-23 by directing Phase 2 to proceed; Phase 1 remains open and none of its exit criteria are presumed satisfied.
- After the NFR-04-shaped measurement, the user selected the available browser profile provisionally for M0; the actual pilot device remains unselected.

- UI-first direction (2026-10-23): desktop 3D office home; data views one click away; warm low-poly style; deterministic local records labeled “Sample” where canonical APIs do not yet exist; work-changing actions stay disabled without real persistence/authorization. User later directed Phase 3 work after Phase 2 completion. Project, agent-definition, and skill-library surfaces now use APIs; remaining UI previews are presentation-only and do not waive Phase 1 safety gates.
