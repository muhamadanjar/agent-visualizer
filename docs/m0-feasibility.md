## Decision summary

- The M0 3D spike has one state-owned adaptive DPR control and passed production-build checks for movement, collision, click-to-move, blocked destinations, camera switching, and local interaction. Performance evidence varies by browser lifecycle: an earlier visible managed-Chromium run at a rounded 1441×900 / DPR 1.25 measured 54–60 FPS idle and 57–60 while moving; the final managed-browser tab run used exactly 1440×900 CSS / DPR 1.25, reported `document.visibilityState=visible`, and held alternating W/S movement for 20 seconds with follow camera, 50 avatar instances, and 10 synthetic event streams. Its five 4-second RAF samples were 51/41/43/56/52 FPS and UI diagnostics were 47/41/46/58/51 FPS; every active sample exceeded 30 FPS. Idle-only/hidden-headless observations varied and included sub-30 FPS, so this is a narrow pass for the specified active workload, not a general frame-rate guarantee or pilot-hardware acceptance. Actual pilot hardware remains unselected; the scene remains non-operational and has no runtime connection.

OMP v18.12.3 passed narrow real RPC task, input-dialog, abort, and interactive allow/deny probes; these do not demonstrate Managed safety. The approval `select` frame has no `toolCallId`, and the current bash approval probe is unverified and must not run on the host. The isolated M0 adapter previously completed one real read-only task; idle-health behavior was verified without a model call. A separate no-provider Bubblewrap smoke now starts installed OMP, negotiates RPC v2, and reads idle `get_state`. It copies the Bun executable through a no-follow descriptor and stages only OMP's declared runtime dependency closure to a private `/tmp` directory, then mounts that tree read-only after clearing inherited environment and setting only sandbox `PATH`/`HOME`. It fails closed if host HOME overlaps the read-only `/usr`, `/lib`, or `/lib64` mounts. It submits no prompt and makes no provider call; this is process-start/health evidence, not adapter integration or task execution. A bounded local resource smoke also passed CPU-time, address-space, file-size, and cgroup process-count controls with negative controls, no provider/network access, and cleanup. It does not prove aggregate resource bounds or production task isolation. Synthetic fixtures verify active-task health reporting and cancellation ordering/idempotency, but the changed task smoke and real adapter cancellation path remain unverified. Activity frames still use single-active-task-window attribution. The initial child probe exposed `bash` despite the parent's `--tools=read,task` allowlist; the explicit read-only agent profile does not constrain unspecified/default agents. Recovery still reopens a session without replaying the interrupted prompt. No exactly-once or at-least-once replay guarantee is proven.

### Runtime gate

Keep Managed runtime integration blocked on approval scope/identity, default child tool scope, production OMP adapter/workspace sandbox integration and resource limits, active-run health, cancellation safety under side effects, and interrupted-task reconciliation. OMP idle health and generic Bubblewrap/resource controls are verified; active-task health, production adapter isolation, and live cancellation safety are not. The no-tools provider harness accepts `http://localhost:20128/v1`. `cl/thinkingmachines/inkling-small:free` completed one text-only task through OMP: one forwarded request, HTTP 200, no denied egress, and matched request-ID lifecycle/result. Other selected models returned HTTP 503/410, or HTTP 200 followed by an aborted task. The local Ollama inventory is unusable (`ollama show` returned `model not found`).

The separate no-provider [`sandbox-egress-smoke.ts`](../spikes/m0-runtime/sandbox-egress-smoke.ts) proves only local mock filtering and Bubblewrap-to-Unix-socket transport. The provider-task harness uses a no-tools synthetic prompt, a fixed local 9Router target, a one-request maximum, a 64-token cap, bounded response size, and tracked upstream cancellation. The first supplied-base attempt stopped before inference because the model catalog exceeded the 256 KiB cap; the cap was raised to 2 MiB. Three selected OpenRouter `:free` routes returned HTTP 503; the requested Muse route returned HTTP 410. Two additional routes returned HTTP 200 but OMP aborted. The direct `cl/thinkingmachines/inkling-small:free` route completed successfully with `agent_start`, `agent_end`, and a settled task result. The successful evidence is text-only: tools were disabled, so tool-call capability is unverified. Catalog metadata's `:free` suffix does not establish zero cost or an account spend cap.

## Phase 1 closure conclusion

Phase 1/M0 feasibility is closed for the user-directed provider-inference and 3D scope based on the bounded request and provisional browser-scene evidence above. This closure establishes neither universal compatibility nor operational Managed readiness; the actual target device remains unselected.

Managed execution remains blocked: no production Provider Adapter, Agent Office-owned tool loop/authorization, workspace and credential isolation, lifecycle event attribution, or recovery was proven. The one user-authorized `:free` request did not verify pricing or an account hard cap; spend and egress controls are required before any further real requests. No Managed MVP claim is supported.

Recommendation: keep the canonical task/run/session/event model and Runtime Adapter contract vendor-neutral; retain OMP as a currently evidenced adapter candidate, not as the product core. ## Orca orchestration boundary

The user selected the installed `orca-ide` CLI for orchestration only. Its `orchestration gate-create`, `gate-resolve`, and `gate-list` commands are documented for coordinator-owned Task-DAG decisions, not runtime tool approvals. Do not repurpose those gates for per-invocation tool authorization. The bare `/usr/bin/orca` is GNOME Orca screen reader; `orca-ide` is the intended CLI in this environment.

Agent Office owns the future approval decision, policy enforcement, and audit. A valid decision must be authenticated and bound to a one-time nonce, workspace/project/task/run/session, stable runtime invocation ID, exact action, normalized parameter/resource hash, expiry, and approver identity. Agent Office must re-check current payload and policy and reject stale or replayed decisions.

OMP v18.12.3's observed approval `select` frame lacks `toolCallId`. Thus Orca orchestration IDs or adapter-generated temporal IDs cannot prove which OMP tool invocation was approved. No Orca decision gate was created and no approval integration code was implemented or tested. Approval remains fail-closed until Agent Office's call-bound approval path exists and the runtime or a mediated tool path supplies stable invocation identity.
